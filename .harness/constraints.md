# 제약

번호는 `M-NN` 으로 고정한다. charzing 의 `C-NN` 과 섞이지 않게 접두를 다르게 뒀다.

> 문서에 "반드시 X" 를 적을 거면 **확인할 검사를 같이 만든다.**
> 못 만들면 "권장" 으로 낮춘다. 검사 없는 규범은 지켜지지 않는다.

## M-01 — 점수 규칙은 두 리포에서 같아야 한다

**검사**: `score-parity` · **상태**: 켜짐 (baseline 3건, 기한 2026-10-09)

크롤러(`minnat-crawler`)가 계산해 DB `weighted_score` 에 넣는 점수와, 웹(`minnat`)이
화면에서 다시 계산하는 점수가 같은 규칙을 따라야 한다.

**정본은 웹이다** (2026-09-25 결정). `CLAUDE.md` 의 점수 공식도 웹과 같다.

```
저장 (크롤러) = min(base × diversity × position_weight × 100, 100)
화면 (웹)     = 저장값 × viewDecay(view)
```

`decay` 는 저장하지 않는다. 뷰별 곡선이 4개(`hot`·`recent`·`midterm`·`alltime`)고
"지금" 에 의존해서, 저장하면 다음 날 틀린 값이 된다. 렌더 시점에만 곱한다.

### 왜 기계가 봐야 하나

두 숫자가 각각 다른 화면에 나온다.

| 숫자 | 계산 | 어디에 |
| --- | --- | --- |
| `weighted_score` | 크롤러 `scorer.calculate_score` | 매일 찍히는 진영 스냅샷 ("파랑 37% vs 빨강 63%") |
| 화면 점수 | 웹 `calculateIssueScore` / `calculateEventScore` | 홈 · 이슈 목록 · 정치인 페이지 · 정렬 |

규칙이 갈려도 **화면 어디에도 그 사실이 안 보인다.** 한쪽 PR 만 보는 사람은
영원히 모른다. 2026-09-25 실측에서 이미 갈라져 있었다 — 크롤러에 다양도와
상한이 빠져 있었고, 크롤러 독스트링조차 코드와 달랐다.

### 무엇을 보는가

1. `CRIMINAL_STAGE_WEIGHT` · `MEDIA_LEAN` 의 키와 값이 두 리포에서 같은가
2. 진영 다양도 계단값(0.7 / 1.0 / 1.3)이 같은가
3. 크롤러 최종 점수식이 다양도와 100 상한을 포함하는가

### 무엇을 안 보는가

- **`decay`** — 저장할 수 없으므로 비교 대상이 아니다
- **`POSITION_WEIGHT`** — 웹에 정의는 있으나 **읽는 코드가 없다**
  (2026-09-25 실측: `constants.ts:62` 정의 외 참조 0건). 실제로는 크롤러가
  계산해 DB 에 넣은 `issue.position_weight` 를 쓴다. 지금 검사에 넣으면
  "웹에 5개가 없다" 는 위반이 뜨는데 고칠 방법이 죽은 상수를 지우는 것뿐이다.
  **죽은 정의를 지운 뒤에 넣는다.**

## M-02 — 진영 집계에 기본값을 두지 않는다

**검사**: `camp-tally` · **상태**: 켜짐 (위반 0)

`camp` 을 한쪽과만 비교하고 나머지를 `else` 로 받으면, 값이 무엇이든 그쪽에 얹힌다.
2026-09-29 실측으로 **세 곳**에 있었다.

```
crawler  scorer.py:130   generate_daily_snapshot
web      score.ts:116    calculateScores
web      score.ts:203    calculateEventScores
```

전부 `camp === "blue"` 뒤 맨 `else` → 빨강이었다. 지금 DB 에 blue/red 만 있어
증상이 없었지만, **정치 중립이 설계의 중심인 서비스에서 진영 집계의 기본값이
한쪽인 것 자체가 결함**이다. 제3정당·무소속을 담는 순간 조용히 한쪽 몫이 된다.

그리고 이 실패는 화면에 안 보인다. `bluePct + redPct` 가 100 으로 맞춰지므로
잘못 얹힌 만큼이 그냥 상대 진영 비율로 나타난다.

**요구**: 두 진영을 각각 명시적으로 비교하고, 어느 쪽도 아니면 세지 않는다.

### 판정이 두 번 틀렸다 — 기록해 둔다

① `else` 와 `red` 의 **위치**를 견줬더니 `else if (camp === "red")` 에서 else 가
   앞이라 **고친 코드를 위반으로** 잡았다
② "맨 else" 로 바꿨더니 창이 블록을 넘어가 `x = a if c else 50` 의 삼항 else 를 잡았다

지금은 **"red 를 비교하는가"** 하나만 본다. 구문을 흉내내려다 두 번 틀렸고,
있어야 하는 것이 있는지만 보면 구문을 몰라도 된다. 창을 넘어가도 최악이
누락이라 안전하다.

## M-03 — 출처 독립성은 낙관적이다 (알려진 한계)

**검사 없음** · 고치지 않기로 한 것이라 기록만 남긴다

점수의 다양도 배수(0.7/1.0/1.3)는 **독립 출처 수**로 정한다. 계열 매체는
한 곳으로 묶지만(`MEDIA_GROUPS`), **통신사 받아쓰기는 못 거른다.**

연합뉴스 기사를 그대로 옮긴 매체 다섯 곳을 지금은 다섯 곳으로 센다.
실제로는 한 곳이다.

### 왜 안 고치나

**① 데이터에 신호가 없다.** `raw_articles.content` 는 기사 전문이 아니라
RSS·네이버 요약이다 (2026-10-01 실측: 1,739건 중앙 125자, 연합뉴스 83자).
같은 사건의 다른 매체 쌍 1,447개를 재니 **유사도 중앙 0.17**, 0.8 이상이
5개(0.3%)뿐이었다. 받아쓰기가 흔한데도 안 보인다 — 매체마다 티저를 다르게
잘라 쓰기 때문이다. 기다려서 쌓일 종류가 아니다.

**② 이 오차는 편향이 아니라 잡음이다.** 받아쓰기는 진영과 무관하게 일어난다
— 연합 기사를 받아쓰는 건 한겨레도 조선일보도 똑같이 한다. 이 서비스의 대표
숫자는 **비율**이라 대칭 잡음은 거의 안 흔든다. 반면 진영 분류 오류는 편향이라
비율을 직접 밀고, 그래서 그건 점수에서 뺐다 (M-01 아래 경위).

**③ 고치려면 기사 본문이 필요한데 그건 저작권 결정이다.** URL 마다 HTTP 요청
1회(실행당 최대 466회) + 매체별 파서가 들고, 무엇보다 전문 보관은 AI 헤드라인을
쓰는 이유(원문 제목조차 저장 안 한다)와 충돌한다. 기술 판단이 아니다.

**④ 근거 없는 상수를 넣지 않는다.** "통신사가 섞이면 할인" 도 검토했으나,
연합+한겨레+조선이 보도했을 때 받아쓰기인지 독립 취재인지 **가를 근거가 없다.**
일괄 할인하면 진짜 교차검증까지 깎는다.

### 다시 볼 조건

기사 본문 수집을 하기로 결정하면 그때 붙인다. `raw_articles.content` 에 긴
글이 들어오면 지금 구조 그대로 작동한다. 그 전에는 **이 값이 낙관적이라는 걸
알고 쓴다.**
