## 0. 한 줄 결론

**엔진은 이미 상당히 견고하지만(87 테스트, 진태양시·절기 UTC 비교), 제품은 "로그인 벽 뒤에 4회 무료가 숨어 있는 구조"라 지나가는 사람이 써볼 수 없다.**
가장 큰 레버는 순서대로 ① 비로그인 미리보기(원국 계산은 공짜) ② "회원 = 계정당 1회 무료" + 이후 유료 ③ 5개 타입을 서로 다른 "질문"에 답하게 분리 ④ 서머타임·표준시 이력 보정(엔진 검증 최우선 갭)이다.

### 1.4 "다시 보면 같은 결과가 나오나?"
- **같은 차트 + 같은 타입 + 같은 해 + 같은 고민 → 같은 문장**이 나온다 (Redis 캐시 → DB `ai_sections` 저장).
- `refresh=true`("다시 풀이받기")만 새로 생성하고 캐시를 덮어쓴다. 캡 차감.
- **해가 바뀌면(`:y2027`) 자동으로 새 해석**이 생성된다. 세운이 바뀌므로 의도된 동작.
- 결함: **Redis가 비워지면(무료 플랜 만료·키 로테이션) DB에 `ai_sections`가 있어도 LLM을 다시 호출**한다. 캐시 미스 시 DB 조회 폴백이 없다(`reading/route.ts:617~634`). 비용 누수 + "어제 본 것과 문장이 다르다" 불만의 원인이 될 수 있다.
- 결함: `concern`이 캐시 키에 들어가므로 고민 한 글자만 바꿔도 새 LLM 호출. 무료 캡이 유일한 방어선.

## 2. "지나가다 써보게" 만드는 유입 구조

### 2.1 핵심 원리
사주 서비스의 전환 병목은 항상 **"생년월일시 입력 → 결과 도달"** 사이의 마찰이다. 원국(8글자) 계산은 LLM 비용이 0이므로 **비로그인에게 공짜로 줘도 손해가 없다.** 돈이 드는 것은 AI 문장뿐이다.

### 2.2 제안: 3단 계단<!-- 캬 똑똑하고만 그냥 아주 -->
```
[0단] 비로그인   폼 입력 → 원국 8자 + 일주 카드 + 오행 그래프 + "나는 어떤 사람" 2문장(템플릿, LLM X)
                  ↓  "전체 풀이 보기" 버튼 → 로그인(카카오 1탭)
[1단] 회원       계정당 1회 무료 (5개 타입 중 아무거나 1개)
                  ↓  쓰면
[2단] 획득       공유 가입 1명 → 1회 / 궁합 초대 수락 → 양쪽 1회 / 日 7일 연속 → 1회
                  (결제 없음. PG 미보유. 월 비용 킬스위치로 지출 상한)
```

- 0단의 "나는 어떤 사람" 2문장은 이미 있는 `buildCoreDesc()`(일주+신강약+격국 합성)로 충분하다. LLM 없이도 개인화된 느낌이 난다.
- 0단 결과 화면 하단에 **블러 처리된 AI 섹션 제목 6개**("연애 스타일", "2026년 흐름"…)를 보여준다. 내용은 가리되 제목은 노출 → 로그인 동기.
- 로그인 직후 **폼 재입력 없이** 바로 풀이가 시작돼야 한다. 현재 `sessionStorage` 폼 보존 로직이 있는지 확인 필요(`saju-page.tsx:1952` 프로필 프리필은 로그인 후만 동작).

## 3. 회원·데이터·재조회 운영 정책

### 3.1 저장 원칙 (제안)
| 데이터 | 저장 | 근거 |
|---|---|---|
| 출생정보 (`user_profiles.birth_*`) | 저장, 본인 수정 가능 | 재입력 마찰 제거. 이미 구현 |

| 고민(`concern`) | 저장 | 이력 UX. 단 민감정보 가능성 → 삭제 기능 필수 |

### 3.2 동일성 정책 — "같은 걸 줄지" (추천안 채택, 결정됨)

| 타입 | 재조회 시 | 이유 |
|---|---|---|
| 命 종합 | **같은 해 안에서는 동일**. 해 바뀌면 새 풀이(현재 동작 유지) | 원국은 불변. 문장이 매번 바뀌면 신뢰도 하락 |
| 緣·財 | 동일 (연 단위 갱신) | 상동 |
| 日 오늘 | 날짜마다 새로 (현재 동작) | 일진이 바뀜 |
| 合 궁합 | 동일 (두 차트 조합 키) | 상동 |
| "다시 풀이받기" | **획득 크레딧 소모 (결정됨)**. 크레딧 0이면 버튼을 획득 안내로 | 현재는 덮어쓰기 → 이전 문장이 사라짐. 유료라도 이전 버전은 보관(`saju_readings` 버전 컬럼 또는 별도 테이블) |

핵심 수정 2가지:
1. **캐시 미스 → DB `ai_sections` 폴백** 추가. Redis 유실 시에도 LLM 재호출 없이 동일 문장.
2. **프롬프트 버전을 캐시 키에 포함**(`{ver}`가 이미 있으나 프롬프트 변경 시 올리는 규율 필요). 프롬프트 개선 후 "옛 풀이"가 섞이는 문제 방지.

### 3.3 무료 정책 — "하루 한 편 + 획득형 크레딧" (2026-09-17 개정)
현행 "로그인 유저 일 4회 롤링 캡"을 폐기하고:

```
로그인 계정 = 타입 무관 하루 한 편 무료 (KST 자정 리셋)
  → 다섯 편(命·日·緣·財·合)을 다 보려면 5일, 급하면 크레딧
이미 읽은 풀이 재열람 = 무제한 무료 (LLM 호출 자체가 없다)
다시 풀이받기 = 크레딧 1 소모
궁합 초대 수락 = 하루 한 편과 무관하게 양쪽 무료 + 양쪽 +1
크레딧은 결제가 아니라 행동으로 획득:
  - 내 공유 링크로 친구 1명 가입     → +1
  - 궁합 초대를 상대가 수락          → 양쪽 +1
  - 7일 연속 풀이 열람               → +1
```
- **결제 없음.** 사업자등록·PG 가 없어 지금은 못 붙인다. PG 비용은 첫해 약 37만원(가입비 22만 + 연관리비 11만 + 통신판매업 등록면허세 4만), 이후 연 15만원 + 세금 신고 의무. 풀이 1건 3,000원이면 본전에 120건 이상 필요. **획득 행동(공유·초대) 수치가 나온 뒤에 등록 여부를 판단**한다. <!-- 이건 언젠가 사용량이 많이 늘면 api로 붙이고 제일 중요한건 사용성이 좋아야해. 일일로 매일매일 한번씩 운 확인하려고 해보는 사람도 있거든. 근데 사용성이 안좋으면 바로 이탈한다. -->
- 구현: Redis 일일 카운터(`saju:cap:free:{uid}:{date}`) 제거 → **Supabase 원장** `saju_credits`(uid, balance, events[]). `009-credit-events.sql`이 이미 있으니 재활용 검토. Redis는 휘발성이라 원장으로 부적합.
- **왜 바꿨나**: 결제가 없는데 "계정당 1회"로 두면 소진한 사람은 돈으로도 못 뚫는 막다른 길에 갇힌다. 하루 한 편이면 기다리면 열리고, 다섯 편을 5일에 걸쳐 보게 되니 재방문 훅이 된다.
- 오늘 몫 소진 UI: 블러 + "오늘 한 편은 이미 읽었어" + 다음 편까지 남은 시간 + 크레딧 얻는 법 3줄 + 읽은 풀이 다시 보기. 랜딩에는 다섯 편 진행 점(N/5)과 "읽음" 표시.
- 어뷰징 가드: 공유 가입 보상은 가입자가 실제로 풀이 1회를 완료한 뒤 지급. 같은 IP·기기 가입은 미지급.
- **월 비용 킬스위치 (필수)**: 결제 수익이 0이므로 지출만 존재. Redis `saju:spend:{YYYYMM}` 에 호출 수 누적, 한도 초과 시 신규 풀이를 "이번 달 무료분 소진" 안내로 차단(또는 Haiku 강등). 한도는 월 3,000회(2026-09-17 결정). 구성에 따라 약 $40~120. 이 한도에 닿을 만큼 쓰이면 사업자등록·PG 를 검토할 시점으로 본다. 어드민은 면제.
- **日(오늘의 사주)은 매일 1회 무료 (코멘트 반영, 결정됨).** 매일 운 확인하러 오는 사용자를 위한 훅. 크레딧 미소모. 플랜 P2-2.
- 광고(카카오 AdFit·AdSense, 개인 가입 가능)는 결과 페이지 1뷰당 1~3원 수준이라 풀이 1회 비용(약 50원)을 못 덮는다. 상쇄 수단이지 수익 모델은 아님. 복채 후원 링크(토스·카카오페이 송금)는 해금 조건 없이 자발적 후원으로만.

### 3.4 비용 가드
- 비로그인 0단: LLM 0원. IP 레이트리밋만.
- 로그인 1단: 계정당 1회 → **회원당 무료 LLM 호출 상한 = 1회**. Sonnet 5 기준 회당 약 4센트 추정(입력 2.5k·출력 3.5k 토큰 가정, $2/$10 per 1M). 회원 1만 명이어도 무료분 총 $400 수준.
- 시스템 프롬프트에 프롬프트 캐시(`cache_control`) 적용. 단 지금 system 문자열에 이름·현재 대운이 섞여 있어 캐시가 안 걸린다 → 규칙 12개(불변)만 system에 두고 이름·대운은 user 메시지로 옮겨야 캐시가 작동한다.
- 실측 필요: `STATUS.md`가 지적한 대로 **지금까지 비용은 전부 추정**. `reading/route.ts`에 `usage` 로그를 찍고 1주 실측 후 결정.

### 3.5 개인정보
- 출생일시+이름은 개인정보. **탈퇴 시 CASCADE**는 `011`에 있음(`ON DELETE CASCADE`).
- 공개 공유(`/saju/view/[id]`)는 **출생정보를 노출하는지 확인** 필요. `public/[id]/route.ts:20`이 `birth_year…birth_name`을 select한다 → **생년월일·이름이 공개 링크로 새 나간다.** 공유 뷰에는 일주·오행·AI 문장만 내려주고 출생정보는 제거해야 한다.
- 궁합 상대 정보: "상대의 동의를 받았는지" 체크 문구.

## 4. 사주 엔진 검증 계획

### 4.1 발견된 갭 (우선순위순)

**① 한국 표준시·서머타임 이력 미반영 — 가장 중요**
`engine.ts:271` `fromKST()`가 **KST = UTC+9 고정**이다. 실제 한국은:

| 기간 | 표준시 | 영향 |
|---|---|---|
| 1908-04-01 ~ 1911-12-31 | UTC+8:30 | 1880~1911생 (실사용자 거의 없음) |
| 1948~1951 (매년 여름) | 서머타임 +1h | 70대 후반 |
| **1954-03-21 ~ 1961-08-09** | **UTC+8:30** | **65~72세** — 부모 세대 궁합 입력 |
| 1955~1960 (매년 여름) | 서머타임 +1h | 상동 |
| **1987-05-10 ~ 1988-10-09** | **서머타임 UTC+10** | **38~39세** — 핵심 사용자층 |

시주는 2시간 단위라 1시간 오차는 **약 50% 확률로 시주가 틀린다.** 1987~88년 5~10월생은 지금 서비스에서 시주가 절반쯤 틀린 채 나가고 있을 가능성이 있다. 수정은 `fromKST()`에 날짜 구간별 오프셋 테이블 하나 추가하는 정도로 작다. **자동 적용으로 결정됨** — 사용자 토글 없이 항상 보정하고, 해당 구간 출생자에게는 결과 화면에 "서머타임/표준시 보정 적용됨" 한 줄 표시. 테스트 케이스: 1987-07-15 23:30(서머타임 적용 시 표준시 22:30 → 亥시, 미적용 시 子시로 날짜까지 바뀜).

**② 외부 기준 대조 없음**
`SAJU_BUILD_PLAN.md`에 "세운 KASI 대조", "대운 교운나이 외부 교차검증 3개"가 미완으로 남아 있다.

**③ 통변(LLM 출력) 품질 QA 없음**
"통변 모순/몰개성 차단 + 블라인드 QA"가 M1 미완. 프롬프트에 규칙 12개가 있지만 검증한 적이 없다.

### 4.2 자동 검증 (스크립트로 한 번에)
| 대상 | 기준 소스 | 방법 | 규모 |
|---|---|---|---|
| 일주(日柱) | 한국천문연구원 음양력 API(공공데이터포털 `LrsrCldInfoService`) — 응답에 **일진 간지** 포함 | 1900~2050 매일 API 호출 → `engine.ts` 일주와 전수 비교 | 55,000일. 일 1회 배치 |
| 월주 경계 | KASI 24절기 특일정보 API | `seolgi.json` 5304건 vs KASI 절입 시각 비교. ±1분 초과 건 리스트업 | 1건씩 |
| 음력 변환 | 동일 API (음력↔양력, 윤달) | `lunar.ts` 결과 vs API 1900~2050 전수 | 상동 |
| 연주 입춘 경계 | seolgi 입춘 인스턴트 | 매년 입춘 ±1분 케이스 자동 생성 | 200케이스 |

이 4개는 **정답이 공식 기관에 있으므로 LLM·사람 판단 없이 100% 자동화**된다. 골든 테스트 43개보다 훨씬 강한 보증이 된다.

### 4.3 수동 교차검증 (학파 차이가 있는 것)
| 대상 | 비교 대상 | 케이스 |
|---|---|---|
| 시주·야자시 | 포스텔러 만세력, 정해사주 만세력, 사주J | 23:00~01:00 출생 10건 |
| 대운 교운나이·순역 | 위 3곳 | 양남·음남·양녀·음녀 × 순/역 = 8건 + 절기 직후 출생 4건 |
| 신강약·격국·용신 | 명리 서적 예제(자평진전·적천수 해설서) 명식 | 20건. **일치율 70%면 정상** (학파별 차이 존재) |
| 궁합 등급 | 없음 (정답 부재) | 극단 케이스로 방향성만 확인: 일지 육합 vs 육충 |

기록: `docs/saju-verification-log.md`에 케이스·출처·일치 여부를 표로. 불일치는 "학파 차이"인지 "버그"인지 분류.

### 4.4 LLM 통변 QA
1. **모순 검출 자동화**: 출력 JSON을 규칙 검사. 신강 차트에 "인성 보강" 문구 → fail. 팩트시트에 없는 신살명 → fail. 정규식 + 금지어 리스트로 충분.
2. **몰개성 검출**: 서로 다른 차트 20개의 출력을 임베딩해 코사인 유사도 > 0.9 쌍 리스트. 높으면 프롬프트가 차트 팩트를 안 쓰는 것.
3. **블라인드 QA**: 사주를 아는 지인 3명에게 본인 사주 풀이 + 무작위 타인 풀이 2개를 섞어 "어느 게 내 것 같나" → 3명 중 2명 이상 맞히면 통과. 통과 못 하면 개인화 실패.
4. 각 타입별 최소 5개 차트 × 2회 생성 → 같은 차트에서 **핵심 판단(신강약·직업군·상대 유형)이 바뀌지 않는지** 확인. 표현은 달라도 판단이 흔들리면 신뢰 붕괴.

## 5. 5개 타입 특화 전략 — "전부 다 해보고 싶게"

원칙: **다섯 개가 서로 다른 질문에 답해야 한다.** 지금은 命이 연애·직업·올해를 다 다루므로 緣·財를 볼 이유가 약하다. 命은 "지도", 나머지는 "확대경"으로 포지셔닝한다.

### 命 종합 사주 — "나는 어떤 사람인가"
- **역할**: 첫 진입 기본값. 신뢰 형성. 다른 4개로 보내는 허브.
- **현재**: 6섹션(본질·연애·직업·올해·내년·한마디). 연애·직업이 緣·財와 겹침.
- **특화**:
  - 연애·직업 섹션을 **각 2문장 티저로 축소**하고 섹션 끝에 "→ 緣에서 상대 유형·시기까지" 딥링크. 命이 나머지를 파는 구조.
  - 대신 命에만 있는 것: **대운 타임라인 10년 단위 전 생애 요약**(이미 대운 타임라인 UI 있음), 궁위별(연·월·일·시) 가족 관계, 용신 기반 "나를 살리는 것/죽이는 것" 카드.
  - 공유 카드는 命 결과에서 생성(일주 한자 + 한 줄). 지금도 있음.
- **재방문 트리거**: 매년 1월 "2027년 세운 풀이가 갱신됐어" 알림(캐시 키 `:y` 구조가 이미 이를 지원).
- **무료**: 계정당 1회에 포함. 첫 진입 기본값이므로 무료 1회가 여기서 쓰일 확률이 가장 높다.

### 日 오늘의 사주 — "오늘 뭘 조심할까"
- **역할**: **유일한 일간 재방문 훅.** DAU를 만드는 건 이것뿐.
- **현재**: 4섹션, 날짜별 캐시, 원국 위에 일진 얹는 프롬프트. 개인화 강화 미완(M1).
- **특화**:
  - 결정에 따라 日도 유료. 매일 재방문 훅이 필요하면 "日만 매일 1회 무료" 예외를 검토(3.3 리스크).
  - 결과를 **한 화면 카드 3개**(에너지 점수 1~5·집중 1줄·조심 1줄)로 극단적으로 짧게. 4섹션 장문은 매일 안 읽는다.
  - **"오늘의 궁합"**: 프로필에 궁합 상대가 저장돼 있으면 "오늘 걔랑은?" 한 줄 추가 → 合과 연결.
  - 푸시/이메일 옵션: 아침 8시 "오늘 일진 甲子 · 너한테는 편재의 날". 카카오 알림톡은 비용 발생, 웹푸시는 무료.
  - 7일 연속 열람 → 크레딧 1 (3.3절).
- **검증 포인트**: 일진 계산이 KST 자정 기준인데 야자시 사용자에겐 23시부터 다음날 일진. 사소하지만 "밤 11시 반에 봤더니 내일 걸 보여줬다" 문의 가능.

### 緣 연애운 — "나는 왜 늘 이런 사람에게 끌리나"
- **역할**: 가장 공유되는 타입. 20~30대 여성 비중 높은 시장의 주력.
- **현재**: 5섹션(민낯·인연의 모습+시기·결혼운·피해야 할 유형·매력). `loveFocusSignals()` 렌즈 구현됨.
- **특화**:
  - **"피해야 할 유형" 섹션을 공유 카드로**. "나를 망치는 상대: 말 잘하는 火 기운 남자" 류의 한 줄이 스레드에서 돈다.
  - **인연 시기 → 캘린더 UI**: 대운·세운에서 배우자성이 들어오는 해를 타임라인에 점으로 찍기. 문장보다 강하다. 데이터는 factsheet에 이미 있음.
  - **바로 궁합으로**: 결과 하단 "지금 만나는 사람이 있다면 → 合" 버튼. 緣이 合의 유입구.
  - 미혼/기혼/연애중 상태를 폼에서 받아 프롬프트 분기(결혼운 섹션이 기혼자에겐 무의미).
- **무료**: 계정당 1회에 포함.

### 財 직업·재물운 — "나는 월급형인가 사업형인가"
- **역할**: 남성·30대 유입. 이직·창업 고민 시즌(연초·연말) 검색 트래픽.
- **현재**: 5섹션(직업군 3개·직장vs사업·재물·타이밍·환경). `careerFocusSignals()` 렌즈 구현됨.
- **특화**:
  - **"직장인 vs 사업가" 판정을 게이지 1개로 시각화**(정재:편재, 관성:식상 비율). 공유용.
  - **타이밍 섹션 → 연도 타임라인**(緣과 동일 컴포넌트 재사용). "2028 이직 유리 / 2031 창업 주의".
  - 고민 입력을 **선택지로 구조화**: "이직 고민 / 창업 고민 / 투자 성향 / 지금 직업이 맞나". 자유 텍스트보다 프롬프트 분기가 정확하고, 캐시 키가 4종으로 수렴해 비용도 준다(현재는 고민 텍스트마다 새 LLM 호출).
  - 재물 섹션에 단정 금지 프레임 유지(이미 프롬프트에 있음). 투자 권유로 읽히면 안 됨.
- **무료**: 계정당 1회에 포함.

### 合 궁합 — "우리는 왜 끌리고 왜 부딪히나"
- **역할**: **바이럴 엔진.** 한 명이 쓰면 두 명이 가입할 수 있는 유일한 타입.
- **현재**: `compat.ts` 엔진(천간합충·지지합충·오행보완·십신역학·5등급) + 프롬프트 + 페이지 구현. 상대 정보를 **내가 직접 입력**하는 구조.
- **특화**:
  - **초대 링크 모드**: 내 생일만 넣고 링크 생성 → 상대가 자기 생일 입력 → 둘 다 결과 열람. 상대는 가입 시 크레딧 5를 받으므로 자연 가입. **상대 생일을 몰라도 궁합을 볼 수 있다**는 점이 기존 앱 대비 차별점.
  - **결과 비대칭**: 초대한 쪽은 전문, 초대받은 쪽은 요약 + "내 사주도 보기"(0단 미리보기로 연결).
  - 등급('천생연분'~'주의') 대신 **"끌리는 이유 3 / 부딪히는 이유 3"** 카드. 낮은 등급이 나오면 공유 안 한다. 이유 카드는 나빠도 공유된다.
  - 연인 외 **친구·동료·부모 궁합** 프리셋. 프롬프트 페르소나만 바꾸면 됨. 사용 범위가 3배.
  - **오늘의 궁합**(日과 연결): 두 원국 위에 오늘 일진 → "오늘 같이 결정하기 좋은 날/피할 날".
- **무료**: 계정당 1회에 포함. 초대받은 쪽은 가입 시 무료 1회를 궁합에 쓰게 유도.
- **운영 (결정됨)**: 상대 출생정보 저장. 고지 문구 + 상대 이름 선택 입력 + 이력에서 삭제 버튼.

### 타입 간 연결 지도
```
검색/공유 → [0단 미리보기] → 命 (허브)
                                ├→ 緣 → 合(초대) → 상대 가입 → 命
                                ├→ 財
                                └→ 日 (매일) ←→ 合(오늘의 궁합)
```
"전부 다 써보고 싶게" 만드는 장치 3개: ① 무료 1회 소진 후 나머지 4개는 제목+첫 문장 블러 노출 ② 각 결과 하단에 다음 타입 딥링크 ③ 5개 완주 시 "내 사주 전체 리포트" 같은 보상.

| 서비스 | 구조 | 시사점 |
|---|---|---|

| 사주연 | 하루 1회 궁합 매칭 + 출석 포인트 | 궁합을 매일 재방문 훅으로 씀 |
| ChatGPT/제미나이 | 엠브레인 2026-01 조사: 신년운세를 AI로 본다 40.7%, 점집 방문 18.5% | **범용 AI에 없는 것**으로 싸워야 함 = 정확한 만세력 계산·일관된 결과·저장·공유·궁합 링크 |

우리 차별점 정리: 범용 AI는 (a) 절기·진태양시 계산을 틀리고 (b) 매번 다른 답을 주고 (c) 저장·공유·초대가 없다. 이 셋이 곧 제품 메시지다. "AI가 아니라 만세력이 먼저"를 랜딩 카피에 넣을 것.

| 모델 | 입력 $/1M | 출력 $/1M | 회당 추정(입력 2.5k·출력 3.5k) | 판단 |

| **Sonnet 5** | **2** | **10** | **약 4센트** | **선택.** Haiku의 2배 가격에 Opus급 문장력. Sonnet 4.6($3/$15)보다 싸다 |

- 코드 변경: `reading/route.ts:464` `tier === 'paid' ? 'claude-sonnet-5' : 'claude-haiku-4-5-20251001'` → 둘 다 `claude-sonnet-5`. `compat/route.ts`도 동일.
- Sonnet 5는 `output_config.effort`를 지원한다. 사주 풀이는 추론보다 문장 생성이므로 **`effort: 'low'` 또는 `'medium'`으로 시작**해 블라인드 QA(4.4)로 비교. 낮은 effort는 출력 토큰도 줄어 회당 비용이 더 내려간다.
